Notploy manages servers and holds credentials, so its security posture matters. This section explains the trust boundaries and the practices that keep an installation safe. It is written for operators of self-hosted instances and for Cloud users who own the servers they connect.

<Callout type="info">
Security is a shared responsibility. On **Self-Hosted** you own the host, its exposure and its
updates. On **Cloud**, Notploy manages the control plane, but your servers, your credentials
and your network exposure remain yours.
</Callout>

## Baseline recommendations

1. **Enable HTTPS before exposing the panel.** Put the dashboard behind a domain with TLS, then disable direct `ip:3000` access. See [First login](/docs/core/first-login).
2. **Enable two-factor authentication** on administrator accounts. See [Account security](/docs/core/account-security).
3. **Treat the Docker socket as privileged.** Notploy needs host Docker access to build and run workloads; anyone who can reach the panel effectively has root on the host.
4. **Scope API keys and rotate them.** Use the least privilege needed and revoke keys you no longer use.
5. **Follow production hardening.** See [Production hardening](/docs/core/guides/production-hardening).

## The trust boundary

Notploy itself is a privileged control plane: it can run containers, read configuration and reach your servers. The primary security boundary is therefore **who can authenticate to the panel and with which role**, followed by **what the panel can reach** on the network. Both are addressed in the pages above.
